# Rook recipient context

`ContextService` reads an exact current original or an oldest-first history page for a retained event's source-qualified conversation. `ContextTools` exposes `rook_get_message` and `rook_get_context` to one authenticated connection identity. The trusted embedding binds that identity when it constructs the dispatcher; tool arguments cannot supply or replace it. These callable library services do not activate production webhook registration or add Rook to the unrestricted resident tool registry.

A read requires the exact owner recipient, a retained event still admitted by current subscription policy, and the same conversation as that event. Before and after anchors are mutually exclusive typed variants and must belong to that conversation. A reply reference to another room is descriptive metadata, not permission to follow it. A currently admitted event can authorize reads after settlement and without a claim. Sender filters determine wake/event eligibility; other speakers remain visible within an authorized room's context.

The owner issues an internal read permit containing its authorization revision and retained source evidence. The service checks its current Authorizer before and after the provider read, and checks the owner revision and admission again before releasing content. Network reads happen outside the mailbox so configuration changes can invalidate a pending read. Provider access checks are additional requirements. The Discord adapter loads current configuration for each read and checks it again before returning; HTTP denial, missing messages, access unavailability, malformed coordinates and timeouts are visible errors. Neither a retained preview nor native supplemental bytes confer authority.

The Discord adapter reuses existing authorized `get_message` and `fetch_messages`, including exact returned identity and page-channel validation. The common response has no fabricated gateway occurrence. It describes content as observed now, with authoritative sender, creation/edit timestamps, reply/reference observations, attachment availability and explicit completeness/truncation fields. A versioned native supplement preserves modeled Discord references, attachment fields and known thread-parent metadata without recursive parent bodies. Reading an edited original does not reconstruct an earlier delivered revision.

History responses retain the requested query separately from observed oldest/newest identities and count. `has_more_hint` is a hint, not a guarantee or a claim of complete room history. A page contains one to one hundred requested records at most; returned empty pages remain valid. Oversized responses fail explicitly rather than silently truncate. Four provider reads may run concurrently per service; each provider call has a ten-second deadline and each serialized result is bounded to four MiB. The existing owner access checks also have bounded deadlines. Cloned services share the concurrency limit.

The public provider boundary uses typed queries, capabilities, observations and errors. Unsupported source instances and operations remain typed failures. Discord IDs and rendering stay in its adapter; numeric and opaque common identifiers are distinct. The public validated message-key projection reuses the retained owner codec. Source fields, raw sender and workspace must agree; represented identities and explicit cross-provider references remain descriptive.

Tests exercise the real owner mailbox and tool parser, including wrong principal, room/module/cursor substitution, policy and access revocation while a read is blocked, temporary failures, claim-free reads, original versus preview content, and preserved pagination anchors. Separate local HTTP fixtures exercise the real Discord query adapter and native projections without contacting Discord. These source tests still require the normal native verification gate before publication.

Next work is the durable publication slot in the same recipient owner, then scoped attachments and authenticated webhook/startup integration. Read success, silence and tool errors do not settle an event or disable its subscription.
