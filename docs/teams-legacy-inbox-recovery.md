# Legacy Teams resident inbox cutover

PR410 introduces a persisted live-consumer kind. An older inbox may contain a consumer with the label `dione-live-app-server` but no kind. That label alone cannot prove it was registered by Dione's resident worker. The new reader treats it as a pull consumer. A signed Teams Activity receives a retriable HTTP 503 with no queued notification or reply authority while this ambiguous consumer is primary; the webhook must not receive a false 202. An active record can block genuine live registration until its recorded expiry; an empty inbox therefore does not make cutover seamless.

Before enabling the repaired Teams transport, stop Dione and preserve a complete, owner-only snapshot of the state directory. Inspect the inbox and its queued, leased and consumer state using an offline, reviewed procedure. Do not infer emptiness from the aggregate status count alone if entries could be associated with the old consumer ID. Keep Teams admission disabled while state is ambiguous. No production state was inspected to prepare this procedure.

If the snapshot proves there are **no pending or leased entries**, retain the snapshot and allow the ambiguous pull registration to reach its recorded expiry. Then start the repaired process and register a genuine live resident. During the wait, Teams admission remains unavailable. A new live ID is expected; the old label record is never promoted. Verify a local signed test Activity reaches the new resident and retains its reply authority across restart before enabling ingress. The repository's local fixture covers this empty-inbox, expiry and new-registration path.

If **any pending or leased entry exists, or emptiness cannot be proven**, hold cutover and keep the locked snapshot. There is no supported public queue operation that safely moves an old-ID live-bound Teams event: public handoff, claim, poll and acknowledge deliberately reject the live-thread/provider-key boundary. Do not edit `codex-inbox.json` by hand, use those public tools as a migration shortcut, or discard old entries. A separate reviewed offline transaction is required to inventory exact IDs, leases and thread bindings, preserve provider keys, move or settle each event atomically, and classify any persistence uncertainty. Reconcile any external delivery acceptance before requeueing, because replay could duplicate a delivered turn.

Rollback to the preserved snapshot is straightforward only before any new admission or settlement on the repaired process. Once new state has been written, restoring an older snapshot could lose or replay accepted work. Hold ingress and use a verified forward repair or migration instead of a blind downgrade. Keep the snapshot until every old-ID event and its reply authority has a recorded outcome.
